# PR Policy — фронтенд

Версия **1.0** · 15.11.2026 · изменения — в конце файла.

Правила, по которым проверяется каждый PR в `main`. Это не новый свод:
правила разработки — в [AGENTS.md](../AGENTS.md) и
[FRONTEND.md](FRONTEND.md), здесь — что из них проверяем перед PR и с какой
строгостью. У бэкенда свой `docs/PR-POLICY.md`, общие пункты (G-*) в обоих
одинаковые.

## Как применяется

- **Новый и изменённый код.** Правила относятся к добавленным и изменённым
  строкам. Старый код рядом PR чинить не обязан; найденное — `TODO:` с
  объяснением или отдельная задача.
- **Три уровня проверки:**

  | Кто | Что | Гарантия |
  | --- | --- | --- |
  | CI (GitHub Actions) | lint, lint:fsd, format:check, typecheck, build | для всех, блокирует merge |
  | `/pre-pr-review` (Claude Code) | всё из CI локально + ревью архитектуры и логики по этому файлу | у того, кто работает в Claude Code |
  | Ревьюер PR | решение по WARNING, отклонения, UX и макет | человек |

- AI-ревью не блокирует merge: его выводы не детерминированы. Блокирует CI.

## Severity и статус

| Severity | Что это | Как влияет |
| --- | --- | --- |
| **BLOCKER** | доказанная ошибка логики или регрессия; нарушение правила B в новом коде; проблема безопасности; упавшая обязательная проверка | PR не создаём, пока не исправлено или не принято отклонение |
| **WARNING** | читаемость, сложность, риск без доказательства, правило W | решает ревьюер; в описании PR — что оставлено и почему |
| **SUGGESTION** | необязательное улучшение | не влияет |

Статус отчёта `/pre-pr-review`: `BLOCKED` — есть BLOCKER; `INCOMPLETE` —
обязательная проверка не запущена / упала по окружению / код не закоммичен;
`READY WITH WARNINGS`; `READY` — всё обязательное прошло, замечаний нет.

## Правила

B — BLOCKER, W — WARNING. «Чем» — что ловит нарушение.

### Общие (одинаковые с бэкендом)

| ID | Правило | | Чем |
| --- | --- | --- | --- |
| G-1 | Один PR — одна задача. Перенос файлов — отдельным PR без правок логики | W | ревью |
| G-2 | Поведение и документация расходятся — док правится в том же PR | W | ревью |
| G-3 | Секреты, токены, `.env`, персональные данные — не в коде, логах, доках | B | ревью |
| G-4 | Обязательная проверка упала из-за изменений | B | CI, скилл |
| G-5 | Ветка не `main`, коммиты с префиксом, без атрибуции ИИ | W | скилл |

### Архитектура

| ID | Правило | | Чем |
| --- | --- | --- | --- |
| FE-ARCH-1 | Слои `app → views → widgets → features → entities → shared`, импорт только вниз; слайсы слоя друг друга не импортируют; в слайс — только через `index.ts` | B | Steiger, ревью |
| FE-ARCH-2 | `app/**/page.tsx` и `layout.tsx` тонкие: реэкспорт экрана из `views`, метаданные. Запросов, состояния, разметки нет | B | ревью |
| FE-ARCH-3 | `"use client"` — только где нужен клиент, как можно ниже по дереву; серверный секрет не попадает в клиентский компонент | B | ревью |

### Данные

| ID | Правило | | Чем |
| --- | --- | --- | --- |
| FE-DATA-1 | Серверные данные — только через хуки `api/` слайса; ключи — из фабрики, без литералов; после мутации — инвалидация | B | ревью |
| FE-DATA-2 | Типы сервера — только сгенерированные из Swagger; ручных DTO и `as` на ответ нет | B | ревью |
| FE-HTTP-1 | Один HTTP-клиент `shared/api`, голого `fetch` в компонентах нет | B | ревью |
| FE-AUTH-1 | Токен не читается и не хранится в JS; доступ к `(admin)` проверяется на сервере | B | ревью |

### UI

| ID | Правило | | Чем |
| --- | --- | --- | --- |
| FE-UI-1 | Цвета и шрифты — токены (hex в классах — W); `cn()`; mobile-first от 320px, шаг 8px | W | ревью |
| FE-UI-2 | У экрана с запросом — загрузка, пусто, ошибка; отправка заблокирована на время запроса | W | ревью |

| FE-SIZE-1 | Компонент > 300 строк — W, > 400 — B (кроме сгенерированных) | W/B | скилл |

## Отклонения

Принятое отклонение — комментарий у кода:

```ts
// policy-exception: FE-DATA-2 бэкенд ещё не отдаёт поле в Swagger, задача #12
```

и строка в разделе «Отклонения от PR Policy» описания PR. Без причины —
WARNING.
